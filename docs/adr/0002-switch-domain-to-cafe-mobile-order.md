# 題材を図書館の貸出管理からカフェのモバイルオーダーに変更する

サンプルの題材を「図書館の貸出管理システム」から「カフェのモバイルオーダー」に変更する。DDD とモジュラモノリスの練習用としては、図書館の題材は検証とテストに手間がかかりすぎたため。モジュール構成(DDD 2 つ + CRUD 2 つ)、`public.py` による照会、ドメインイベントによる連携、会員ランクによるポリシー切り替え、import-linter による境界の強制といった、学びたい要素はそのまま移植する。

## 図書館の題材で手間がかかっていた点

- **時間に依存するルールが多い**: 返却期限・延滞・取置期限があり、テストのたびに `today` を差し替える必要があった。延滞検出と取置失効には定期実行の management コマンド(`detect_overdue` / `expire_holds`)が必要で、画面から動作を確かめるのも難しかった。
- **前提データが多い**: 1 回の貸出を試すだけで、書誌・蔵書(個体)・会員を用意する必要があった。
- **連鎖が長い**: 返却 → 取置 → 取置失効 → 次の予約者へ、という連鎖を追う必要があった。

## Considered Options

- **EC の注文と在庫引当**: なじみはあるが、在庫数の整合性(同時実行、引当の解放)に関心が向きやすく、題材として重い。
- **タスク管理(カンバン)**: 最も軽いが、ドメインロジックが薄く、DDD にする理由を説明しにくい。
- **カフェのモバイルオーダー(採用)**: ルールが「ステータス遷移」と「金額計算(割引)」で、時刻に依存しない。前提データは会員と商品だけで済み、画面でも「注文 → 調理開始 → 調理完了 → 受取」の順にボタンを押すだけで流れ全体を確かめられる。

## モジュールの対応

| 図書館 | カフェ | 種類 |
| --- | --- | --- |
| lending(貸出) | ordering(注文) | DDD |
| reservation(予約) | kitchen(キッチン) | DDD |
| catalog(蔵書) | menu(メニュー) | CRUD |
| members(会員) | customers(会員) | CRUD |

## Consequences

- 定期実行の management コマンドはなくなった。すべての状態変化は利用者の操作か、それを受けたドメインイベントで起きる。
- 会員ランクで変わるものが、貸出条件(冊数・期間)から割引率になった。
- 図書館版では lending → reservation を照会の一方向に留めていた。カフェ版では ordering と kitchen の間に照会がなく、イベントだけで双方向にやり取りする(コレオグラフィ)。「調理開始後はキャンセル不可」も照会ではなく、ordering が自分で持つステータスで判定する。
- 図書館版のコードは git の履歴(このブランチより前のコミット)から参照できる。
