# 席からの注文(店内)を ordering の注文として扱い、会計を seating のイベントで開閉する

席に座ったお客様が席から注文できるようにする。席からの注文は会員登録が要らず、キッチンで作ったあと店員が席まで運び(提供)、支払いは席の利用が終わったときにまとめて行う。これを次のように実装する。

- 席からの注文は、ordering の `Order` に「注文の種類」(持ち帰り / 店内)を足して扱う。店内の注文は会員の代わりに**会計 (Bill)** を持ち主にする。
- 会計は ordering の新しい集約。seating が席の利用開始・終了で発行する `SeatOccupied` / `SeatVacated` を ordering が購読し、会計を開く / 支払済にする。
- READY の後は、持ち帰りなら受取 (PICKED_UP)、店内なら提供 (SERVED) に分かれる。

## Considered Options

- **店内用に別の集約(または別コンテキスト)を作る**: 調理チケットとの連携(`OrderPlaced` → チケット → `CookingStarted` / `CookingCompleted` → 明細ごとの進行)と金額計算が持ち帰りとまったく同じなので、二重に持つことになる。違いは「持ち主」と「最後の受け渡し」だけなので、`Order` に種類を足すほうが小さい。kitchen は変更不要。
- **会計を seating に持たせる**: 席の利用 1 回分という単位は seating に近いが、会計の金額は注文から計算するので、seating が ordering を照会する(または注文の金額をイベントで受け取る)必要が出る。seating を「席の状態だけを持つ」まま保ちたいので採らない。
- **会計を最初の注文のときに作る(seating に照会して使用中か確かめる)**: ordering → seating の照会が増え、退席の通知はどのみちイベントで要る。開くのも締めるのもイベントにそろえたほうが分かりやすい。
- **会計を seating のイベントで開閉する(採用)**: 依存は seating → ordering のイベントの一方向だけで、seating は ordering を知らない。「席が使用中か」は ordering が自分で持つ会計の状態(開いているか)で判定でき、照会が要らない(ordering と kitchen の関係と同じ考え方)。

## Consequences

- `Order.customer_id` は持ち帰りの注文だけが持つ(店内では None)。`OrderPlaced` / `OrderCancelled` の `customer_id` も None になりうる。`OrderPickedUp` は持ち帰りだけなので、customers のポイント付与は変わらない。
- 店内の注文には会員ランクの割引・ポイント・進行中の注文数の上限がかからない。
- import-linter で ordering → `seating.domain.events` を許可した(seating の内部には触れない)。
- イベントを同期ディスパッチしているので、退席と会計の締めは同じトランザクションで起きる。席からの注文と退席が同時に来ても、会計の行をロックして読むので、締めた会計に注文は紛れ込まない。
- この機能を入れる前から使用中だった席には会計がない。その席からは注文できないので、いったん退席して案内し直す。
- 退席の時点でまだ調理前・提供前の注文が残っていても、会計はそのまま支払済になる(退席を止めたり、残りの注文を取り消したりはしない)。運用で困るようなら、seating の退席を ordering が止められるようにするか、締めるときに未調理の注文を取り消すかを検討する。
